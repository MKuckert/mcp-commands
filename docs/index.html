Use cases

Where it earns its keep

Three situations where bridging scripts to your agent beats writing a custom server.

Real tooling for sandboxed harnesses

Your agent runs in a container, sandbox, or on dedicated hardware, but you want the real, unrestricted toolchain — a full compiler install, faster builds, hardware-attached utilities. Run the server on that host over HTTP and bridge it into the sandbox: the agent gains capability, the sandbox stays the boundary around the harness — and the server's own trust boundary is its scripts directory (write access there is code execution as the server user).

One agent, many machines

The harness lives on your laptop, the work happens on a Linux build box, a Mac, a Windows host. Platform-specific commands become reachable wherever the agent runs — over the streamable HTTP transport, with auth, TLS, and CORS.

Your scripts, now tools

You already maintain a pile of Bash, Python, Node, Ruby scripts. Drop them into a directory and they become native MCP tools — no custom server to write per script.

Features

Boringly simple. Bounded by design.

Everything you need to expose local utilities to any MCP client — and nothing you have to babysit.

Language agnostic

Bash, Python, Node, Ruby — any executable with a shebang is a tool. (Compiled binaries are discovered too; they just can't carry frontmatter.)

Dynamic discovery

Point it at a directory. Every executable inside becomes a registered MCP tool — automatically.

Hot reloading

Add, modify, or delete scripts while the server runs. --watch picks them up — no restarts.

Auto-documentation

One Description: line in your script's header is all the LLM needs to know what the tool does.

Smart argument translation

LLM JSON becomes CLI flags: {"force": true} → --force. Sorted, validated against the declared schema, passed straight to the process — no shell in between.

Flexible transport

Stdio for local clients like Claude Desktop, or streamable HTTP with auth, TLS, CORS, and concurrency caps for the web.

How it works

Three lines of comment. Zero glue code.

The entire contract between your script and the LLM lives in the first lines of the file.

Drop in a script

Any executable file in your --scripts directory becomes a tool named after the file.

Describe it once

A Description: line — plus optional Param: and Timeout: annotations — is all the frontmatter you'll ever write.

The LLM calls it

Arguments are translated to CLI flags, the script runs with a timeout, and tagged output goes straight back to the model.

scripts/render.sh
#!/bin/bash
# Description: Runs the long-running render pipeline.
# Param: source string required "Source file to render"
# Timeout: 1h 30m 5s

while [ $# -gt 0 ]; do
  case $1 in
    --source) source=$2; shift 2 ;;
    *) shift ;;
  esac
done

echo "rendering $source"
What the server registers
render(source:str)
     Runs the long-running render
     pipeline. (timeout: 1h30m5s)

Install

One command, three ways.

Homebrew, Go, or a prebuilt release — pick whichever fits your platform.

Your machine 
$ brew trust --formula MKuckert/homebrew-tap/mcp-commands
$ brew install MKuckert/homebrew-tap/mcp-commands

macOS / Linux. The brew trust line is a one-time step required for non-core taps.

Your machine 
$ go install github.com/mkuckert/mcp-commands@latest

Requires Go. The binary lands in $HOME/go/bin (or $GOBIN) — make sure that's on your PATH.

Your machine 
$ tar -xzf mcp-commands_0.9.5_linux_amd64.tar.gz   # unzip on Windows

Each release ships mcp-commands_<version>_<os>_<arch> archives for linux/darwin/windows × amd64/arm64 (tar.gz, zip for Windows) plus a checksums.txt. Grab the asset for your platform from the releases page, extract it, and put the mcp-commands binary on your PATH.

Run it

Two flags. One minute.

That's the whole server config: where to run scripts, and where to find them.

Your machine
$ mcp-commands --dir /home/dev/proj \
              --scripts /home/dev/proj/scripts

# HTTP mode for remote clients, bearer auth:
$ mcp-commands --dir /home/dev/proj \
              --scripts /home/dev/proj/scripts \
              --port 8080 --api-key-file token.txt

# TLS: add --tls-cert cert.pem --tls-key key.pem,
#      or put a TLS-terminating proxy (Caddy/nginx) in front
client config
{
  "mcpServers": {
    "mcp-commands": {
      "command": "mcp-commands",
      "args": ["--dir", "/home/dev/proj",
                "--scripts", "/home/dev/proj/scripts"]
    }
  }
}
